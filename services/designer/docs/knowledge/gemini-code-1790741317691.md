# Login Screen Design Knowledge

Reusable practice guidance for designing login and authentication screens across
mobile, tablet, desktop, responsive, consumer, B2B, fintech, healthcare,
e-commerce, education, internal tools, social and entertainment products.

This is a decision framework, not a fixed screen recipe. Do not add every
possible login control by default. Select the smallest clear flow that supports
the product's authentication method, user goal, security level and platform.

## 1. Design objective

A login experience should help the right user authenticate successfully with
minimal uncertainty and effort. It should:

- Make the current authentication method obvious.
- Present only the fields and actions required by that method.
- Establish one clear primary action.
- Explain errors and recovery paths without exposing sensitive account data.
- Preserve user input when safe and useful.
- Provide an appropriate alternative or fallback when the primary method fails.
- Adapt to the product domain, device, accessibility needs and security risk.

Do not assume that every login screen needs email, password, social login,
remember-me, guest mode, registration and a back button.

## 2. Inputs to consider before composing

Before choosing the layout, infer or ask about these dimensions:

1. Authentication method: password, OTP, magic link, social login, SSO, PIN,
   passkey, biometric, or a hybrid flow.
2. Identifier: email, phone number, username, employee ID, workspace, or
   another product-specific identifier.
3. Primary user goal: sign in, continue to a workspace, verify a code, unlock
   an account, or choose an authentication method.
4. Product context: consumer, B2B/SaaS, fintech, healthcare, e-commerce,
   education, internal tool, social or entertainment.
5. Security and privacy level: ordinary account access, sensitive personal data,
   financial action, regulated data, or high-risk operation.
6. Platform and viewport: mobile, tablet, desktop or responsive.
7. Entry context: standalone entry screen, modal, nested flow, invite link,
   checkout, workspace selection or re-authentication.
8. Existing product shell: brand, navigation, typography, color, component
   library and visual language.

When information is missing, use a conventional low-risk pattern and keep
assumptions minimal. Do not invent complex authentication requirements.

## 3. Authentication patterns

Choose one primary pattern. Combine patterns only when the product context
requires it.

### 3.1 Password login

Typical elements:

- Identifier field such as email, phone or username.
- Password field with a visibility toggle when appropriate.
- Primary submit action.
- Password recovery link when recovery is supported.
- Optional alternative authentication or registration path.

Do not add both email and phone fields unless the product explicitly supports
both or lets the user choose an identifier.

### 3.2 OTP or passwordless login

Use a two-step flow when the code is sent after the identifier is submitted:

- Identifier entry state.
- Send-code primary action.
- Verification-code state.
- Resend action with a clear timer or availability rule.
- Change-identifier action.
- Expired-code and invalid-code feedback.

Do not show a password field in a passwordless flow. Keep the code entry easy
to scan, paste and correct.

### 3.3 Magic link

Show the identifier entry first, then a confirmation state explaining where the
link was sent and what the user can do if it does not arrive. Provide resend,
change identifier and support/recovery actions only when relevant.

### 3.4 Social login or SSO

Use provider buttons only when they are an intentional product authentication
path. Consider:

- Provider identity and recognizable icon.
- One consistent button treatment per provider group.
- SSO, organization or workspace context for B2B products.
- A fallback method when the provider is unavailable or not permitted.

Do not let multiple provider buttons compete visually with the main product
authentication path. Choose a hierarchy based on product usage and policy.

### 3.5 PIN, passkey or biometric access

For high-frequency or high-security access, the primary action may be PIN,
passkey or biometric authentication. Include a secure fallback such as account
credentials or device verification when the product supports it.

Use trust and security messaging sparingly. Do not add social login to a
security-sensitive flow without a clear product reason.

### 3.6 Hybrid authentication

Use a method-selection screen only when users genuinely have multiple supported
paths. The selection should lead to a focused sub-flow rather than placing all
fields and providers on one crowded screen.

## 4. Optional screen zones

Treat these as compositional zones, not mandatory components. Select only the
zones justified by the authentication pattern and entry context.

### Brand and context zone

May contain a logo, product name, workspace name, invitation context or a short
security message. Keep it secondary to the authentication task.

### Heading and supporting copy

Use a concise heading that explains the task, such as signing in, entering a
code or continuing to a workspace. Supporting copy should reduce uncertainty,
not become marketing content.

### Identifier zone

Contains the appropriate label, input, helper text, formatting hint and
validation feedback. Use a separate visible label; do not rely on placeholder
text as the only label.

### Secret or verification zone

Contains password, PIN, code or passkey controls only when required. Keep
related recovery, visibility or resend actions close to the relevant control.

### Recovery zone

Use the recovery action that matches the method:

- Password: forgot-password or account-recovery path.
- OTP: resend code, change identifier or use another method.
- SSO: contact organization administrator or choose another provider.
- Biometric/PIN: use the configured fallback method.

### Primary action zone

Use one visually dominant action such as Sign in, Continue, Send code,
Verify code or Use passkey. The label should describe the next action.

### Alternative authentication zone

Use a divider and alternative methods only when they are supported and useful.
The alternative must not obscure the primary path.

### Registration, guest and support zone

Add Create account, Continue as guest, Help or Contact support only when the
product flow supports it. These are secondary paths and should not compete with
the primary authentication action.

### Legal and trust zone

Use terms, privacy, security or consent copy only when required by the product
or jurisdiction. Keep it readable and close to the relevant action.

## 5. Layout and hierarchy

Use a layout that matches the task and platform rather than forcing one recipe.

- Mobile usually benefits from a single focused column, comfortable side
  margins and a clear vertical rhythm.
- Desktop may use a centered form, split brand/form layout or contextual panel
  when that improves orientation without distracting from authentication.
- Tablet should preserve readable form width and touch-friendly controls.
- Responsive layouts should define how the form, brand area, provider buttons
  and supporting content reflow at narrower widths.
- A nested login flow may need a back or close action; a standalone login does
  not automatically need one.
- Use negative space to establish hierarchy. Do not fill empty space with
  decorative cards or unrelated illustrations.
- Keep the primary action visible without requiring unnecessary scrolling.

Recommended starting values are references, not hard constraints:

- Mobile side padding: approximately 16–24 px.
- Comfortable interactive height: approximately 44–48 px or larger.
- Field-to-field spacing: approximately 12–16 px.
- Group spacing: approximately 24–32 px.

Adjust these values to the selected design system, viewport and visual style.

## 6. Interaction and state model

Consider the states relevant to the chosen pattern. Do not render every state
simultaneously; use them to guide the design and content.

### Field states

- Empty/default.
- Focused/active.
- Filled.
- Invalid with a specific correction message.
- Disabled or read-only when the flow requires it.

### Action states

- Enabled.
- Pressed/active.
- Loading/submitting.
- Disabled while an operation is in progress.
- Retry after a recoverable failure.

### Flow states

- Initial entry.
- Code sent or link sent.
- Invalid credentials or invalid code.
- Expired code or link.
- Rate limited or temporarily locked.
- Network/offline failure.
- Authentication success and next destination.
- Fallback method or support path.

For each important error, show what happened and what the user can do next.
Avoid vague messages such as “Something went wrong” when a useful recovery
instruction is available. Avoid revealing whether a particular account exists
when that would create a privacy or security risk.

## 7. Accessibility and usability

- Give every field a persistent, meaningful label.
- Preserve a logical keyboard and screen-reader focus order.
- Keep touch targets comfortable and sufficiently separated.
- Use text, iconography and layout in addition to color for state communication.
- Maintain readable contrast for text, controls, errors and disabled states.
- Keep error messages close to their fields and announce important status
  changes where the platform supports it.
- Support paste and autofill for email, phone and verification codes where
  appropriate.
- Do not make password visibility, resend or recovery actions hard to discover.
- Ensure the design remains usable with large text and narrow widths.

## 8. Domain modifiers

Domain context changes priorities; it does not automatically dictate a fixed
layout.

- Consumer products may prioritize phone, social login, passwordless access or
  account creation.
- B2B/SaaS products may prioritize SSO, organization, workspace and invitation
  context.
- Fintech and other high-risk products may prioritize PIN, passkey, biometric
  access, security messaging and conservative recovery paths.
- Healthcare products may need stronger privacy, consent and support guidance.
- E-commerce products may support phone/OTP and guest checkout when relevant.
- Education products may need institution, student ID or SSO context.
- Social and entertainment products may emphasize fast return access and
  supported social providers.

These are prompts for reasoning, not mandatory components.

## 9. Content guidance

- Use the user's language and the product's established terminology.
- Make the heading task-oriented and concise.
- Use action labels that describe the next step: Sign in, Continue, Send code,
  Verify or Use passkey.
- Keep helper text short and useful.
- Explain password, code and identifier requirements before submission when
  possible.
- Avoid unnecessary promotional copy on a focused authentication screen.
- Keep recovery, registration and alternative-method labels easy to understand.

## 10. Design-system and OpenPencil implementation guidance

The semantic design should be mapped to the selected real design system. Do not
invent a monolithic “login component” when the library provides primitives.

- Model the form as a container with separate label, helper/error text and
  input or verification component.
- Use `kind="component"` for buttons, inputs, password fields, OTP controls,
  checkboxes, alerts, tabs, provider buttons and other reusable primitives.
- Use separate component nodes for repeated provider buttons or code cells when
  the design system supports them.
- Keep only user-visible values in component `content`.
- Put product-specific grouping, hierarchy and intent on container nodes.
- Use exact icon names from the available icon source.
- Preserve the semantic role and select a variant appropriate to the state and
  visual direction.
- Do not assume that a component exists; retrieve and bind the actual design
  system component before rendering.
- Semantic specification should describe the screen, not output JSX. JSX is
  generated later by the page designer from the approved specification.

## 11. Anti-patterns

Avoid:

- Adding every possible authentication method to one screen.
- Showing password recovery on a passwordless-only flow.
- Showing a password field when the selected method is OTP or magic link.
- Making registration, guest access or social login visually equal to the main
  authentication action without a product reason.
- Using placeholder text as the only field label.
- Hiding important errors in a toast or distant banner.
- Creating a narrow mobile-style form stretched across a desktop canvas.
- Using generic cards, excessive gradients or unrelated decoration to fill space.
- Hardcoding one button count, one provider set or one fixed vertical layout.
- Treating a library-default component as a finished visual decision.

## 12. Composition checklist

Before finalizing a login screen, verify:

1. The authentication method and primary user goal are clear.
2. Only the required fields are present.
3. There is one obvious primary action.
4. Recovery and alternative paths match the selected method.
5. Important loading, error, retry and success states are accounted for.
6. The layout fits the target platform and viewport.
7. Labels, focus order, touch targets and contrast are accessible.
8. Copy is concise, actionable and appropriate to the domain.
9. Real design-system components are used where available.
10. The composition has a clear hierarchy and no accidental generic or
    unfinished regions.
